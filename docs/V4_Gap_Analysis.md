# PYTHIA FOREST — GAP ANALYSIS
## V3 → V4 Production Readiness Audit
### 32-Member Specialist Board · Complete Feature Review

**Date:** May 2026  
**Audited file:** pythia-forest-v3.html (1,762 lines, single file, vanilla JS)  
**Board verdict format:** KEEP · IMPROVE · REPLACE · REMOVE · DEFER  
**Priority:** MUST HAVE · SHOULD HAVE · COULD HAVE · POST-MVP

---

## EXECUTIVE SUMMARY

V3 is a **high-quality prototype** that successfully communicates the product vision. The forest metaphor is emotionally resonant, the visual hierarchy is correct, and the care team architecture is well-conceived. However, it is not a production application. It is a single HTML file with no persistence, no real data, no security, no error handling, no accessibility compliance, no offline capability, and no connection to any real system.

**The gap between V3 and production is not a cosmetic gap. It is an architectural one.**

The board's unanimous position: **do not refactor V3 into production code.** Instead, use V3 as the definitive UX specification and design reference, and build V4 as a properly structured PWA against it. Every pixel, every animation, every piece of copy in V3 is worth preserving. The architecture underneath it must be rebuilt from scratch.

This is not a criticism of V3. V3 did exactly what it was supposed to do: prove the vision. V4 must do what V3 cannot: be trustworthy.

## SECTION 1 — USER EXPERIENCE & INTERFACE

### 1.1 The Living Forest Scene (Base Image + Canvas Overlay)
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**What works:**
The layered approach (real image as base + canvas overlay for dynamic elements) is architecturally sound and the right decision for Patient Zero's web app. The visual result is beautiful and emotionally appropriate for a 65+ neurological patient audience.

**What must change:**

**Critical — Image loading failure handling (line 47-48):**
The `onerror="this.style.display='none'"` fallback silently removes the entire forest background when images fail to load. For a patient whose only feedback is the forest, this produces a black screen with no explanation. This is a clinical trust failure.
- V4 must implement: progressive loading with a soft blur placeholder, explicit retry logic, and a graceful fallback that maintains the forest atmosphere even without images (canvas-only mode).

**Critical — `user-scalable=no` viewport meta tag (line 5):**
Disabling pinch-to-zoom is a WCAG 2.1 Level AA violation (Success Criterion 1.4.4). For patients over 65, many of whom have reduced visual acuity, this is both an accessibility failure and potentially a legal liability in markets where WCAG compliance is legally required. The app must be designed so it works correctly WITH zoom enabled — not by disabling it.

**Significant — Canvas `pointer-events: none` blocks accessibility (line 72):**
The dynamic canvas layer sits over the entire scene but has pointer-events disabled. This means the lake-tap interaction relies on a separate canvas event listener that calculates relative Y position (lines 1744-1747). This brittle coordinate calculation breaks on different device sizes and screen orientations. Replace with a proper hit-test abstraction.

**Minor — `object-position: center 30%` is hardcoded (line 50):**
The image crop position is fixed. On different aspect ratios (iPad, landscape phone, desktop browser) the forest image will be incorrectly cropped, potentially removing Pythia from the frame entirely. V4 needs responsive object-position values.

### 1.2 Pythia Speech Bubble
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**What works:**
Font choice (EB Garamond italic), positioning, the caret pointer, the warm cream background — all correct. The floating animation is calming without being distracting.

**What must change:**

**Critical — Static pre-written messages (lines 1610-1623):**
The 12 hardcoded messages cycle on an 18-second interval. There is no LLM, no real personalization, no awareness of the actual time of day, Owen's actual mood, his actual NFB state, or anything that happened in previous sessions. For Patient Zero this is acceptable as a placeholder. It is not acceptable for a pilot. Every message must say Owen's name because it's hardcoded to "Owen" — this breaks for any other patient.
- V4: Messages must be dynamically generated by the Pythia LLM, personalized to the patient, time-aware, and context-aware.

**Significant — No voice output:**
Pythia speaks visually only. For a 65+ patient population with visual impairments, reduced reading speed, or cognitive fatigue, text-only communication is insufficient. The speech bubble must be accompanied by optional voice (TTS). This is also the primary mechanism for passive speech monitoring — Pythia's voice triggers natural patient responses.

**Minor — Bubble position `bottom: 52%` is fragile:**
This fixed percentage positions the bubble relative to viewport height. On small phones (iPhone SE: 667px height), the bubble may overlap the forest floor or the listening indicator. Needs responsive positioning anchored to Pythia's visual position in the image, not a fixed percentage.

### 1.3 Listening Indicator (Three Pulsing Dots)
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**What works:**
The three-dot pulsing animation is universally understood as "listening." Placement below the speech bubble is correct.

**What must change:**

**Critical — It is purely cosmetic. There is no microphone access, no speech-to-text, no actual listening.**
The dots imply to the patient that Pythia is hearing them. This is false. For a vulnerable, cognitively affected patient who believes they are being heard when they speak to the app, this is not a minor UX issue — it is a trust violation with clinical implications. 
- V4: Either (a) implement real speech-to-text immediately, or (b) display the listening indicator only when the microphone is actually active, with a clearly explained consent prompt.

**HIPAA Note (Privacy & HIPAA Specialist):** Always-on microphone collection of a patient's speech requires explicit, informed, written consent documented in the patient record. The current implementation has no consent flow whatsoever. This must be resolved before Patient Zero uses the app.

### 1.4 Bottom Panel — Peek State (Two Pills)
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**What works:**
Two-pill layout is clean and uncluttered. Primary action (Talk to Pythia) is correctly distinguished from secondary (My Forest). Appropriate for 65+ users — low cognitive load.

**What must change:**

**Significant — Touch target sizes:**
Pills have `padding: 11px 20px` which produces approximately 40px height. WCAG 2.5.5 (AAA) recommends 44px minimum; iOS Human Interface Guidelines require 44pt minimum. The 65+ UX specialist notes that arthritic hands and fine motor reduction in neurological patients make this insufficient. Minimum 52px height required.

**Significant — `cursor: pointer` is desktop-only vocabulary:**
On touch devices this property is meaningless. More importantly, there is no visual feedback state between tap and result. The `transform: scale(0.95)` on `:active` is correct but disappears in ~50ms — too fast for older adults. A 200ms minimum feedback duration is required.

**Minor — No haptic feedback:**
Web Vibration API (`navigator.vibrate(10)`) provides a 10ms haptic pulse that significantly improves touch confidence for older adults. One line of code, high clinical value.

### 1.5 Bottom Panel — Drawer (My Forest)
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**What works:**
The drawer concept is correct. Showing domain vitals in a bottom sheet rather than on the main screen preserves the forest's emotional purity. The tier separation (T1 / T2) is clinically appropriate.

**What must change:**

**Critical — Drawer has no maximum height constraint with scroll:**
```css
.panel-drawer { display: none; background: var(--forest-dark); ... padding: 0 20px 44px; }
```
No `max-height`, no `overflow-y: auto`. On small screens the drawer content overflows the viewport with no way to scroll. The Tier 2 vitals grid and action buttons may be completely invisible below the fold.

**Critical — `display: none` / `display: block` for open/close:**
Using `display` toggle means there is no animation on open — the drawer appears instantly. V3's CSS comment says `display: none` but the comment says `.open { display: block }`. This produces a jarring snap with no transition. V4 must use `transform: translateY` with a spring curve.

**Significant — 14-card vitals grid is too dense for 65+ users:**
6 cards at 3-column + 8 cards at 4-column = an extremely dense information grid with 7.5px–9px labels that are illegible for most 65+ users. The Accessibility Specialist notes that minimum body text for this demographic is 16px; minimum label text is 14px. These labels are half the required size.

**Significant — Vital bar fills show health data without explanation:**
The bars communicate relative domain health visually. But there is no tooltip, no label expansion, no way for the patient to understand what "Memory" bar at 65% means vs. 88%. The design principle says no numbers — correct — but patients need some way to understand what they're seeing when they ask.

### 1.6 Connection Status Strip
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**What works:**
The concept of showing connection status to Therapeia at the top of the drawer is clinically important and correctly placed.

**What must change:**

**Critical — It always shows "● Live" regardless of actual state:**
```javascript
const CONNECTION = { THERAPEIA: 'connected', NAVIGATOR: 'pending', EMERGENCY: 'not_set' };
```
These are hardcoded constants. There is no heartbeat, no actual WebSocket, no real status. A patient who sees "● Live" believes their health data is being transmitted. If it is not, this is a false representation of a safety-critical system state.

**Minor — "Therapeia" is not patient vocabulary:**
The patient sees "Therapeia · ● Live." Therapeia is the platform name, not a word a 65-year-old patient would understand or trust. Rename to "Pythia is watching over you" or "Your health signals are safe."

### 1.7 Cave of Knowing
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**What works:**
The cave image as background is beautiful. The consent gate ("Are you sure you'd like to visit the cave today?") is clinically and ethically correct. The once-per-day limit is correct. The 3-second transition ("Pythia rises from the water...") is emotionally powerful.

**What must change:**

**Critical — `caveVisitedToday` resets on page reload:**
```javascript
let caveVisitedToday = false;
```
This is a JavaScript variable. Reloading the page resets it to false. Owen could visit the cave 20 times per day by refreshing the browser. The clinical reasoning for the once-per-day gate (preventing obsessive checking anxiety) is entirely defeated.
- V4: Must persist `caveVisitedToday` in localStorage with a midnight-reset timestamp.

**Critical — Cave domain readings are static hardcoded strings:**
Every cave reading is written in advance. "The birch is thirsty. It asks only for a short walk..." is beautiful, but it will say exactly the same thing every single day regardless of whether the birch has improved, worsened, or stayed stable. For Patient Zero this is immediately noticeable and trust-destroying.
- V4: Cave readings must be LLM-generated, incorporating actual domain trend data.

**Significant — Sphere canvas position is hardcoded:**
```css
#sphereCanvas { position: absolute; top: 8%; left: 50%; transform: translateX(-50%); width: 200px; height: 200px; }
```
The sphere is placed at 8% from top of the cave image. On different device heights, the sphere will sit over Pythia's body, over the cave entrance, or outside the cave entirely. Position must be responsive to the image's natural composition.

**Significant — The sphere animation runs `requestAnimationFrame` with a boolean flag:**
```javascript
let sphereAnimating = false;
function leaveCave() { sphereAnimating = false; }
```
When `sphereAnimating` is set to false, the `drawSphere` function returns immediately — but the previously queued `requestAnimationFrame(drawSphere)` still fires once more. In practice, this causes one extra frame to render. More importantly, there is no `cancelAnimationFrame` call, meaning animation frame handles accumulate if the cave is opened and closed repeatedly.

### 1.8 Care Team Module
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**What works:**
Three-tab architecture (Medical / Emergency / Navigator) is correct. Dual-path completion (Pythia-guided vs. manual) is a strong clinical and UX decision. Emergency contact with relationship field, sensitivity toggle, and confirmation SMS concept is exactly right.

**What must change:**

**Critical — No data persistence:**
Every form field resets when the page is reloaded. This is the most fundamental failure for a real patient. Owen fills in his emergency contact (his wife Maria), closes the app, reopens it — everything is gone.
- V4: All care team data must be encrypted and persisted (localStorage for PWA, secure cloud sync for multi-device).

**Critical — Form validation is absent:**
Phone number fields accept any string. There is no format validation, no required-field enforcement, no error states. A patient could "save" an emergency contact with a blank phone number and believe Pythia will call someone in an emergency.

**Critical — The "Let Pythia ask" path is non-functional:**
```javascript
function activatePythiaGuide() {
  document.getElementById('pythiaGuidedSection').style.display = 'block';
}
```
This shows a static strip with one button that triggers `showToast('Pythia will begin asking in your next conversation.')`. There is no next conversation. There is no Pythia conversation engine. This is a toast notification pretending to be an AI feature.

**Significant — Emergency contact confirmation SMS is a stub:**
```javascript
triggerEmergencyContact({ type: 'confirmation', timestamp: Date.now() });
```
This function logs to the console. No SMS is sent. The patient believes their emergency contact has been notified. They have not been.

**Significant — No encryption of sensitive data:**
The care team stores names, phone numbers, doctor information, insurance IDs, and medication data. None of it is encrypted. Storing this in `localStorage` unencrypted is a HIPAA violation.

### 1.9 Navigation (Bottom Nav Bar)
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**What works:**
Four-item nav (Forest / History / Pythia / Settings) is correct in structure. Active state indication on "Forest" is correct.

**What must change:**

**Significant — Three of four nav items are non-functional:**
- "History" → `showToast('Forest history coming in Phase 2')`
- "Pythia" → `talkToPythia()` (cycles pre-written text, not a real conversation)
- "Settings" → `showToast('Settings opening...')`

For Patient Zero, these items should either be functional or visually unavailable (greyed out with an explanation). Tapping a navigation item and receiving a toast that says "coming in Phase 2" is disorienting and trust-damaging for a vulnerable patient.

## SECTION 2 — TECHNICAL ARCHITECTURE

### 2.1 Application Structure
**Verdict: REPLACE**  
**Priority: MUST HAVE**

**Current state:** Single 1,762-line HTML file with all CSS, HTML, and JavaScript inline.

**Why this must change:**
- Untestable: No unit tests can be written against inline JavaScript
- Unmaintainable: A bug in the care team logic requires searching through 1,762 lines
- Unscalable: Adding a new feature means modifying this single file
- Uncacheable: The browser cannot cache individual JS modules or CSS files separately
- Undeployable: There is no build pipeline, no environment variables, no minification

**V4 structure (PWA):**
```
/public
  index.html          (shell only, <1KB)
  manifest.json       (PWA manifest)
  service-worker.js   (offline + cache strategy)
/src
  /components         (UI components)
  /screens            (Forest, Cave, CareTeam, Settings)
  /services           (API hooks, NFB engine, BLE)
  /stores             (State management — Zustand or Jotai)
  /hooks              (useNFB, usePythia, useBluetooth, usePermissions)
  /utils              (encryption, date, formatting)
  /config             (environment, API endpoints, feature flags)
  /assets             (images, audio, fonts — hashed for cache busting)
/tests
  /unit
  /integration
  /e2e                (Playwright)
```

**Recommended stack:**
- **Framework:** React 18 (Vite build) — component model is necessary for maintainability
- **State:** Zustand (lightweight, no boilerplate, works offline)
- **Styling:** CSS Modules + CSS custom properties (no Tailwind — too much bloat for a single focused app)
- **Canvas:** OffscreenCanvas where supported (moves rendering off main thread)
- **PWA:** Workbox (Google) for service worker generation
- **Build:** Vite (fast, tree-shaking, code splitting)

---

### 2.2 State Management
**Verdict: REPLACE**  
**Priority: MUST HAVE**

**Current state:**
```javascript
let pIdx = 0;
let caveVisitedToday = false;
let sphereAnimating = false;
let DW, DH, tick = 0;
```
Global mutable variables scattered throughout the file. No state management. No persistence.

**V4:**
Zustand store with the following slices:
- `patientStore` — name, PCCA profile, preferences
- `nfbStore` — 14 domain states, strength values, trend history
- `careTeamStore` — providers, emergency contact, Navigator connection
- `sessionStore` — caveVisitedToday (with timestamp), current speech index
- `connectionStore` — Therapeia, Navigator, Bluetooth connection states

All stores persist to encrypted localStorage. `sessionStore.caveVisitedToday` auto-resets at midnight.

### 2.3 Data Persistence
**Verdict: REPLACE**  
**Priority: MUST HAVE**

**Current state:** No persistence whatsoever. All state is in-memory JavaScript variables.

**V4 persistence layers:**

| Data Type | Storage | Encryption | Notes |
|---|---|---|---|
| Patient profile & PCCA | localStorage + cloud sync | AES-256-GCM, key in device secure storage | Survives browser cache clear via cloud |
| NFB domain history | IndexedDB | AES-256-GCM | Large time-series, needs structured storage |
| Care team data | localStorage + cloud sync | AES-256-GCM | PHI — must be encrypted at rest |
| Conversation history | IndexedDB | AES-256-GCM | Needed for continuity |
| Cave visit timestamp | localStorage | None required | Non-PHI, single timestamp |
| Session state | sessionStorage | None required | Cleared on tab close intentionally |
| Media documents | Cloud (Cloudflare R2 or AWS S3) | Server-side AES-256 + client-side envelope | Photos, PDFs — too large for localStorage |

### 2.4 Canvas Architecture
**Verdict: IMPROVE**  
**Priority: SHOULD HAVE**

**Current state:**
```javascript
function drawOverlays(t) {
  dCtx.clearRect(0, 0, DW, DH);
  // ... all drawing logic in one 80-line function
  requestAnimationFrame(drawOverlays);
}
requestAnimationFrame(drawOverlays);
```
Single monolithic draw function runs forever. No frame rate cap. No dirty-checking (redraws every frame even when nothing has changed). Will drain Owen's iPhone battery within hours of leaving the app open.

**V4:**
- Cap at 30fps for ambient animations (forest glow, ripples, fireflies)
- Only redraw when state changes (dirty flag pattern)
- Move canvas rendering to OffscreenCanvas + Web Worker on supporting browsers
- Pause all animation when app is backgrounded (Page Visibility API)
- Resume on foreground with smooth fade-in

---

### 2.5 Animation Performance
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**Current issues identified:**
- `filter: brightness() saturate() hue-rotate()` CSS transitions on the `<img>` element (line 52) cause full GPU re-composite on every frame during transitions. On older iPhones this causes visible jank.
- Multiple simultaneous `requestAnimationFrame` loops (`drawOverlays` + `drawSphere`) with no coordination
- The sphere canvas is 200×200 at `window.devicePixelRatio = 1` — appears blurry on Retina displays (all modern iPhones). Canvas dimensions must be multiplied by `devicePixelRatio`.

---

### 2.6 Error Handling
**Verdict: REPLACE**  
**Priority: MUST HAVE**

**Current state:** Zero error handling anywhere in the application.

Critical missing error handling:
- No `try/catch` around any async operation
- No handling for `requestAnimationFrame` failure
- No handling for canvas context unavailability
- No handling for font loading failure (EB Garamond from Google Fonts — fails with no internet)
- No global error boundary
- No crash reporting

**V4:** Every async operation wrapped in try/catch. Global `window.onerror` and `window.onunhandledrejection` handlers. Crash reporting to Sentry (self-hosted for HIPAA compliance). Graceful degradation for every failure mode.

---

### 2.7 Font Loading
**Verdict: IMPROVE**  
**Priority: MUST HAVE**

**Current state:**
```css
@import url('https://fonts.googleapis.com/css2?family=EB+Garamond:ital,wght@0,400...');
```
Fonts are loaded from Google Fonts CDN on every page load. This means:
1. Requires internet connection to render correctly
2. Google receives the patient's IP address on every app open (GDPR concern)
3. If Google CDN is slow, the entire app renders in system fallback font for 1-3 seconds
4. Font loading is render-blocking on first load

**V4:** Self-host all fonts in `/public/fonts/`. Use `font-display: swap` with a carefully chosen fallback stack that matches the rhythm of EB Garamond. No external font CDN.

## SECTION 3 — SECURITY & PRIVACY

### 3.1 Authentication
**Verdict: REPLACE**  
**Priority: MUST HAVE**

**Current state:** No authentication whatsoever. The app opens to Owen's forest with no login. Anyone with the URL sees Owen's data.

**V4:** Passkey authentication (WebAuthn) as primary. No passwords. Biometric (Face ID / Touch ID) unlocks the app. For web PWA, this maps directly to the Apple/device biometric. No username, no password, no "forgot password" flow — appropriate for 65+ users and eliminates phishing risk.

---

### 3.2 Data Encryption
**Verdict: REPLACE**  
**Priority: MUST HAVE**

**Current state:** No encryption of any kind.

**V4:** 
- All localStorage data encrypted client-side with AES-256-GCM before storage
- Encryption key derived from device biometric (via WebCrypto API + platform credential)
- IndexedDB entries individually encrypted
- All API calls over TLS 1.3 minimum
- No PHI ever logged to browser console or analytics

---

### 3.3 Content Security Policy
**Verdict: REPLACE**  
**Priority: MUST HAVE**

**Current state:** No CSP headers. The app is vulnerable to XSS injection.

**V4 CSP:**
```
Content-Security-Policy: 
  default-src 'self';
  script-src 'self';
  style-src 'self';
  img-src 'self' blob: data:;
  font-src 'self';
  connect-src 'self' wss://api.therapeia.health https://api.therapeia.health;
  media-src 'self' blob:;
  worker-src 'self';
  frame-ancestors 'none';
```
No inline scripts. No `eval`. No external CDN dependencies.

---

### 3.4 HIPAA Compliance
**Verdict: REPLACE**  
**Priority: MUST HAVE — BLOCKER**

**Current state:** Zero HIPAA compliance. PHI (name, medical information, care team data) stored in plaintext JavaScript variables.

**Minimum HIPAA requirements for V4 MVP:**
- [ ] BAA with all cloud providers (Cloudflare, AWS, or GCP with HIPAA BAA program)
- [ ] Encryption at rest for all PHI
- [ ] Encryption in transit (TLS 1.3)
- [ ] Access controls (authentication before any PHI displayed)
- [ ] Audit logs for all PHI access
- [ ] Breach notification procedure documented
- [ ] Patient right to delete their data (implemented)
- [ ] Business Associate Agreements with any third-party AI providers (OpenAI, Anthropic, etc.)

**Note from Regulatory Specialist:** Before Patient Zero uses this app with real health data, minimum HIPAA technical safeguards must be in place. The current V3 prototype should only be used to demonstrate the UX — never with real patient data.

## SECTION 4 — AI & CONVERSATION

### 4.1 Pythia Conversation Engine
**Verdict: REPLACE**  
**Priority: MUST HAVE**

**Current state:** 12 hardcoded strings cycling every 18 seconds.

**Gap:** This is the single largest functional gap in V3. Everything else could be tolerated as prototype behavior. A conversation engine that does not converse is not Pythia.

**V4 requirements:**
- Real-time LLM inference (recommended: Claude claude-sonnet-4-6 as primary via Anthropic API)
- Conversation memory persisted across sessions
- PCCA profile injected into system prompt
- NFB domain states injected into context on each turn
- Time-of-day awareness
- Emotion-tracking across conversation turns
- Structured output extraction (detect PCCA signals, domain observations, escalation triggers)
- Voice input (Whisper via Web Speech API or native iOS)
- Voice output (TTS — ElevenLabs or iOS AVSpeechSynthesizer via PWA bridge)

---

### 4.2 NFB Engine
**Verdict: REPLACE**  
**Priority: MUST HAVE**

**Current state:**
```javascript
function mockNFBStream(onUpdate) {
  setInterval(() => {
    const d = all[Math.floor(Math.random() * all.length)];
    const delta = (Math.random() - 0.5) * 0.03;
    d.strength = Math.max(0.1, Math.min(1, d.strength + delta));
    onUpdate(d);
  }, 9000);
}
```
Domain strengths are random walks. There is no NFB logic, no Bayesian model, no Random Forest, no actual signal processing. The forest responds to noise.

**V4:**
The NFB engine is a separate service (not in the frontend). The frontend receives domain strength updates from the NFB service via WebSocket. The frontend renders what it receives. The computation logic belongs in the backend.

---

### 4.3 Apple Watch Integration (Bluetooth)
**Verdict: DEFER → IMPLEMENT FOR PATIENT ZERO**  
**Priority: SHOULD HAVE**

**Current state:** No Bluetooth, no HealthKit, no sensor integration of any kind.

**For Patient Zero (web PWA):**
Apple Watch data cannot be accessed via Web Bluetooth API on iOS Safari — this is an Apple restriction. However, Apple Health (HealthKit) data can be accessed via a Web App with proper iOS web app manifest configuration when added to Home Screen as a PWA.

**Recommended path for Patient Zero:**
- Use Apple Health app on Owen's iPhone as the intermediary
- Apple Watch automatically syncs HRV, sleep, activity, heart rate to Apple Health
- The Pythia PWA requests HealthKit read permissions via a small Swift bridge (WKWebView + native plugin)
- This requires the app to be wrapped in a minimal native shell — one screen, one permission request, then hands off to the PWA

**This is the first case where the PWA-only approach hits a wall.** The board recommends: build the minimal native wrapper (Swift/Xcode, ~200 lines of code) that grants HealthKit access, then serves the PWA inside it. This is Option A.5 — a hybrid between pure PWA and full React Native.

---

### 4.4 Eye Tracking via Camera
**Verdict: DEFER**  
**Priority: POST-MVP**

**Current state:** Not implemented.

**Assessment:** Camera-based eye tracking via the web is technically possible (WebGazer.js, MediaPipe Face Mesh) but requires:
- Consistent lighting
- Consistent device position
- Calibration session before each use
- Significant CPU usage (affects battery and animation performance)
- Explicit camera consent with clear explanation

For a 65+ patient in varied home environments, the signal quality will be insufficient for clinical use without careful protocol design. The board recommends deferring this until after the pilot generates data on what Tier 2 sensors actually add clinical value.

**Exception:** Eye blink rate and gross gaze direction can be extracted passively during Pythia's video conversation mode with reasonable reliability. This is worth exploring in Phase 2 alongside the native iOS implementation.

## SECTION 5 — DOCUMENT INGESTION (New Feature)

### 5.1 Architecture
**Verdict: ADD (new feature)**  
**Priority: SHOULD HAVE for Patient Zero**

**Board assessment:** Document ingestion — the ability for Owen to photograph or upload his medical records, discharge summaries, imaging reports, and prescriptions — is one of the highest-value features for the pilot. Owen's founding narrative is about fragmented records. This directly addresses it.

**Recommended implementation for V4:**

```
Patient uploads document (photo/PDF/DOCX)
    ↓
Client-side: compress + encrypt before upload
    ↓
Upload to Cloudflare R2 (HIPAA BAA available)
    ↓
Server-side: OCR (AWS Textract or Google Document AI)
    ↓
Structured data extraction (LLM — extract medications, diagnoses, dates)
    ↓
Embedding (text-embedding-3-large or equivalent)
    ↓
Vector store (Pinecone or pgvector in Postgres)
    ↓
Pythia can now answer: "What did my last MRI say?" 
Navigator can see all documents in structured format
Therapeia indexes for population analytics (anonymized)
```

**In the forest UX:** Document upload is accessed only through the "Care Team" module, never from the main forest screen. Pythia introduces it conversationally: "Owen, would you like to show me your last scan report? I can read it and keep it safe."

## SECTION 7 — CLINICAL SAFETY ASSESSMENT

*From the Clinical Safety Officer, Neurologist, and Neuropsychologist:*

**V3 does not pose clinical risks in its current form because it contains no real patient data and no real AI.** However, the following risks emerge the moment real data is connected:

**Risk 1 — False sense of monitoring:**
The listening dots suggest active monitoring. If Owen believes Pythia is monitoring his speech and she is not, he may forgo seeking care based on the assumption that Pythia would have flagged something. This is an active safety risk.
**Mitigation:** Never imply monitoring is active when it is not. All monitoring indicators must reflect actual system state.

**Risk 2 — Cave readings that don't match reality:**
Static cave readings that say "the birch is doing well" when Owen's gait has actually deteriorated could provide false reassurance. This is the most serious clinical risk in V3.
**Mitigation:** Cave readings must be dynamically generated from real NFB data, reviewed by clinical advisors for safe framing, and never provide false positive reassurance.

**Risk 3 — Emergency contact stub:**
If Owen experiences a neurological event and Pythia attempts to contact his emergency contact through the stub function, nothing happens. No one is called.
**Mitigation:** Emergency escalation must be fully functional before Patient Zero uses the app for real. This is a patient safety blocker.

## AMENDMENT — PANEL DECISION: MAY 2026
### Domain Cards Removed from Patient-Facing Interface
**Authority:** 32-Member Specialist Board · Unanimous  
**Approved by:** Ron Engelberg

### Decision

The domain vital cards, domain bars, tier labels, connection status strip, and all NFB domain visualizations are **REMOVED** from the patient-facing Pythia Field interface.

**Verdict change — 1.5 Domain Cards (previously IMPROVE → now REMOVE)**

| Element | Previous Verdict | New Verdict | Reason |
|---|---|---|---|
| 14 domain vital cards | IMPROVE | **REMOVE** | Clinical anxiety risk |
| Domain bars (visual) | IMPROVE | **REMOVE** | Patient learns to read them, performs not expresses |
| Tier 1 / Tier 2 labels | IMPROVE | **REMOVE** | Meaningless and alarming to patient |
| Connection status strip | IMPROVE | **REMOVE** | Creates monitoring anxiety |
| "Your six trees" drawer section | IMPROVE | **REMOVE** | Forest itself communicates this |
| Drawer — domain grid | IMPROVE | **REMOVE** | Replaced by 3-action drawer |

### What Replaces the Domain Drawer

The bottom drawer now contains exactly three elements:

```
┌─────────────────────────────────┐
│  ━━━ (handle)                   │
│                                 │
│  [🌿  Talk to Pythia      ]     │
│                                 │
│  [🪨  The Cave            ]     │
│                                 │
│  [🏥  Care Team           ]     │
└─────────────────────────────────┘
```

Nothing else. No bars. No labels. No status. No data.

### Clinical Justification (Panel Summary)

1. **Psychologist:** Visible health metrics cause monitoring anxiety and reduce quality of life in neurological patients. Equivalent to a bedside vital signs monitor the patient watches all day.

2. **Neuropsychologist:** Patient awareness of what is measured causes performance behavior rather than natural expression. NFB clinical data quality degrades in direct proportion to patient awareness of measurement domains.

3. **UX Specialist (65+):** Domain bars shift emotional register from "I am safe here" to "what is wrong with me today" — irreversibly within a session.

4. **Neurologist:** Domain data is a clinical construct meaningful only to clinicians with context. Without that context, patients assume the worst.

5. **Clinical Safety Officer:** This is a patient safety decision, not a UX preference. False self-interpretation of domain data is a documented pathway to inappropriate ER visits and psychological decompensation.

### What Is NOT Changed

- The forest continues to reflect domain health states visually (tree condition)
- The NFB engine continues collecting all 14 domain measurements
- The cave continues showing domain information — in Pythia's voice, once per day, on request
- Navigator continues showing all domain data to clinicians
- Zero clinical data collection is reduced

### Three-Layer Patient Information Architecture (Final)

```
LAYER 1 — THE FOREST (always visible)
  The forest condition communicates health state
  No labels. No explanation needed.

LAYER 2 — PYTHIA'S VOICE (on interaction)
  Warm, contextual, domain-aware
  No clinical language. No metrics.

LAYER 3 — THE CAVE (once per day, patient-initiated)
  Deep domain readings in forest language
  Pythia explains. Patient listens.
```

**All domain data remains fully available to clinicians via Pythia Navigator.**
